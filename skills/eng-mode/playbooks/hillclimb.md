### Hillclimb

**You own the metric and the experiment's integrity. Supervise and review; delegate the attempts.** For sustained, iterative improvement of one measurable thing against a target ("hillclimb on X", "make startup 50% faster", "systematically drive down <metric>", "keep trying until <metric> improves by N%"). A one-off fix is Bug fix or Perf issue; this is the loop.

Core discipline: one change, one measurement, keep or revert. Never stack untested changes, and never claim a win from code inspection. The data decides (the **prove-it-works** principle skill).

1. Ground the workload and architecture with `how`. Name the realistic dimensions that move the result (for example data size, history, state, and concurrency), choose a case that reproduces the complaint, and link each likely bottleneck to the architecture mechanism that causes it. If no case reproduces it, fix the repro first. Define one metric, the direction that counts as better, and a checkable stop predicate of `target AND minimum attempts`; use the user's numbers, or record explicit target and attempt-floor defaults before measuring.
2. Build a sensitive, repeatable harness whose command prints one numeric metric. Prove sensitivity with contrasting realistic workloads: the target case must reproduce the symptom and an easier case must separate in the expected direction. If the ruler cannot distinguish them, revise it before continuing. Freeze the command, inputs, and aggregation; report the median of N runs, with N recorded and large enough to clear noise. Record the baseline and a green regression gate. Any later change to the ruler, workload, aggregation, or inputs invalidates every prior number: stop that run, explain the discontinuity, and re-baseline a new run.
3. Invoke `goal` for the improvement outcome. Invoke `loop` with a prompt naming the frozen metric predicate and a limit, or use a blocking watcher when the measurement command itself waits. The goal and loop use the same `target AND minimum attempts` predicate. For unattended execution, borrow only Autonomous run's wake mechanism, never its stop rule.
4. Open `show-me-your-work` and keep its gitignored `decisions.tsv` outside the changed tree so it survives candidate reverts. Log one row per attempt: id, architecture-grounded hypothesis, change, before, after, delta, tests, verdict (`kept` or `reverted`), note. Read it before every attempt so rejected mechanisms are not retried accidentally.
5. Each iteration tests one mechanism-grounded hypothesis with a tight candidate scope. Delegate the attempt; the lead reviews the diff. Parallelize only independent, non-conflicting work: race analysis or patch proposals as distinct `local://` artifacts, or use truly independent owned paths; never race competing writers against the shared tree or use `isolated: true` for candidates that would auto-apply. Apply candidates to the measured tree serially.
6. Measure each candidate before and after with the frozen ruler and run the regression gate. Accept only movement beyond noise with behavior intact; otherwise revert the attempt in full. For each accepted fix, stage only its owned changed paths, create one commit, and check that committed state before beginning the next candidate. Never stack unmeasured changes. Correctness and simplicity outrank the metric: revert a numeric win that breaks behavior, and keep a simplification that holds the number.
7. After each measurement, the lead checks the target, minimum-attempt floor, plateau, and loop limit. A plateau is a pivot signal, not a stop: after repeated rejects, change mechanism category, combine compatible near-misses, re-read or instrument the source, or try a more radical architecture-grounded hypothesis. Record `no_progress` and the escalation in `decisions.tsv`.
8. Stop only when the full predicate is met, or when the remaining ideas are genuinely marginal relative to their cost. Never relax the predicate, stop while cheap untried hypotheses remain, or let an unattended-run rule override this policy. If stuck, surface the blocked mechanism and remaining hypotheses instead of spinning. At a successful stop, record measured evidence, stop `loop`, then complete `goal`; at the loop limit, OMP stops the loop and the lead reports the unmet predicate.
9. Run Opening a PR with accepted commits stacked in the order they landed, preserving each before/after comparison and dependency order.

**Reply:** the metric direction and full stop predicate, baseline to final with the percent delta, iterations run (kept vs reverted), each accepted fix on one line, the `decisions.tsv` path, final goal/loop state, any stuck mechanism or unmet predicate, and the best idea you would try next if pushed further.
