### Worktree cleanup

**Inventory first. Classification recommends an action; it never authorizes deletion. Every removal requires the user's choice of an exact audited path.** Worktree deletion can destroy state that no review or branch can recover, so ownership, recoverability, and authorization are separate gates; passing one never implies the others.

1. Bound the audit before inspecting disk. Record the repository root and the exact parent directories in scope. Enumerate worktrees from `git worktree list --porcelain`; inventory dot-prefixed siblings only within those exact parents so hidden worktrees are not missed. Do not turn a filesystem search result, guessed path, simulator, cache, OMP session store, browser profile, or user application state into a cleanup candidate. Simulator and cache cleanup is outside this playbook and must be reported as excluded.
2. Create an auditable before-inventory keyed by canonical path. Record exact filesystem free-space output and, for every exact path, source of discovery, bytes, age, branch or detached state, HEAD SHA, upstream, dirty tracked files, all untracked files, ignored artifacts, stash or checkpoint references, PR state through the selected provider, and a preliminary `active`, `WIP/scratch`, `clean merged`, `abandoned`, or `ambiguous` classification. `wip:N` means N tracked uncommitted paths; `scratch:N` means N untracked or ignored paths and does not mean they are disposable. Preserve the command evidence and exact path list; totals alone are insufficient.
3. Map ownership before recommending anything. For each path, name the human, OMP session, `hub` agent/job, `goal`, `loop`, PR, or process that owns or uses it, with the evidence used for the mapping. Check active and parked `hub` work, managed processes, current goal and loop state, selected-provider PRs, OS processes whose working directory or open files resolve under that exact path, and only exact `history://<id>` sessions already known to reference it. Never scan bare `history://` or unrelated sessions. An unresolved actor-to-path mapping is `ambiguous` and held.
4. Treat any active session, job, agent, goal, loop, process, pinned history session, open PR, or other owner as a hold. Clean merged or apparently abandoned state is only a recommendation. WIP/scratch, tracked changes, untracked or ignored artifacts, detached commits, ambiguous ownership, and in-use state never silently authorize loss.
5. Present the inventory and ask the user to choose, by exact path, `preserve`, `checkpoint/archive then remove`, or `remove and discard`. For every path containing WIP/scratch or any tracked, untracked, or ignored content, itemize what would be lost and require an explicit discard choice or first materialize a user-approved recoverable checkpoint/archive. A general request to "clean up" is not approval to discard uncommitted state.
6. Before an approved removal, record the path's HEAD and every worktree-only commit. Confirm each commit that must survive is reachable through a named branch, tag, stash, or approved archive/bundle outside the worktree. Capture approved ignored artifacts as well as tracked and untracked work; a commit alone is not a complete checkpoint. Re-read ownership immediately before deletion and stop if the path became active or changed since the inventory.
7. Remove only a user-selected canonical path returned by the inventory. Attempt normal `git worktree remove <exact-path>` first. If it refuses, report why and stop; use `--force` only after the user explicitly chooses force for that exact path and the approved recoverable state exists, or explicitly chooses to discard the itemized state. Prune metadata only after the selected removals. Never substitute recursive filesystem deletion or a newly typed path.
8. Produce an exact after-inventory using the same path list and byte measurement as before. Verify every removed path is absent, every preserved or held path remains, and every preserved ref and commit still resolves to the recorded object. Re-enumerate worktrees and scoped hidden siblings, then attribute the byte delta to each removed path; do not claim unrelated free-space changes as reclaimed bytes.

**Reply:** exact before/after filesystem free-space output; exact paths deleted and the user choice authorizing each; actor-to-path ownership and holds; WIP/scratch and ignored artifacts preserved, archived, or explicitly discarded; surviving refs and commit SHAs with resolution evidence; per-path and total reclaimed bytes from the before/after inventory; and the explicitly excluded simulator/cache/session/application-state scope.
