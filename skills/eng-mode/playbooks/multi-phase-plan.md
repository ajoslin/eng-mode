### Multi-phase or multi-PR plan

**You own the delivery map, not execution.** Follow [../references/plan.md](../references/plan.md) and produce its overview plus canonical per-PR phase artifacts. Every phase is one evidence-bearing PR unit with an explicit dependency, accountable owner, branch/base, observable result, file boundary, verification receipt, review gate, and merge or handback operation.

Name the execution playbook for every phase and use the repository-selected forge provider for PR and stack mechanics. When layout, interface, interaction, or timing is uncertain, place a throwaway Prototype phase before production writing and require its branch, head SHA, matching-surface screenshots or observed timings, selected direction, and disposal record.

The operator's plan path wins; otherwise use the repository's documented planning location, then the reference's default. Keep overview material concise and treat each phase artifact as the canonical evidence record for its PR. Append alternatives, risks, evidence index, and execution handback.

End unarmed: implementation remains zero-write until the operator's recorded `go`. Describe, but do not create, the execution `goal`, bounded `loop` or provider watcher, wake condition, limit, and disarm condition. A lightweight plan checker may be named only when repository tooling already supports it; otherwise use the reference's reviewer checklist.

**Reply:** plan paths; ordered PR/dependency graph; owners and branches/bases; execution playbooks and provider operations; prototype gates; exact verification surfaces and evidence lanes; review and delivery gates; risks; handback recipient; and confirmation that no execution mechanism was armed.
