### Autopilot-stack

**Build and verify one dependent, review-first PR chain; the root owns topology and the operator owns landing. Ordinary coherent work stays one PR.**

1. State the protocol and wait when asked for a plan. Begin writes only after an explicit go. On a hold or stop, immediately send every owner a zero-write instruction, stop the loop, and preserve branches, briefs, trails, watcher state, and stack placement for resumption.
2. Assign each PR one persistent accountable owner on an exclusive branch. That owner, or a named successor on the same branch, owns build, provider registration and PR creation through **Opening a PR**, proof on the real surface through `verify-project`, triage, cleanup, its decision trail, and Babysit to merge-ready. Run self-contained owners in parallel; serialize only overlapping writes. Owners never mutate stack topology or land.
3. At each merge-ready head, the root commissions three independent lanes and aggregates `VERIFIED(<sha>)`: repository gates, live real-surface proof, and receipts-plus-diff audit that distrusts the PR body. Each lane returns `PASS`, `PASS+NOTES`, or `FAIL`, pinned to that exact SHA. Any `FAIL` blocks; retain notes in the aggregate verdict. The root never serves as a lane. Post the verdict on the PR and return findings to its owner.
4. `STACK-READY(<sha>)` means `VERIFIED` at that exact SHA, Babysit merge-ready at that SHA, the verdict posted on its PR, and the root has countersigned and safely appended it to the provider-owned topology. A new SHA voids both states unless `git patch-id` proves identity; otherwise the owner fixes forward, all three lanes reverify, and the root countersigns the replacement verdict.
5. The root alone owns topology. It compares current head and base, absorbs trunk or parent drift through the selected provider's documented topology operation, and uses patch identity to decide re-verification. In safe dependency order, it appends only a candidate whose exact SHA is `VERIFIED`, Babysit merge-ready, posted, and countersigned; the successful append establishes `STACK-READY(<sha>)`. Owners report branch tip and intended parent but never run topology commands. Do not serialize independent implementation merely because append order is linear.
6. Use only the selected provider for PR state and watching. Its documented watcher event schema, rearm operation, `READY` / `WAITING` / `ADVANCE` / `COMPLETE` states, arming confirmation, topology operation, merge-when-ready request and disarm, and current-head/base comparison are authoritative; if an operation is missing, stop rather than fall back. Neither root nor owner arms merge-when-ready. The operator lands through **Shipping**.
7. Prefer the provider's blocking wait. When repeated audit turns are required, the main session keeps the objective in `goal` and uses `loop` with an event-driven wake or a 30-minute maximum audit cadence. On every wake, probe each owner and count only side effects—commits, pushes, PR/check/thread changes, proof receipts, topology changes, or trail records—as progress. Replace a stuck owner immediately with a named successor on the same exclusive branch.
8. Deliver one linear chain for bottom-to-top review. Nothing in this playbook merges, closes, or arms auto-merge.

**Reply:** report stack root and tip; for every PR, owner or successor, current head SHA, intended and actual base, `READY` / `WAITING` / `ADVANCE` / `COMPLETE`, Babysit gate, posted `VERIFIED` verdict and lane receipts, `STACK-READY` state, countersign, decision-trail location, and any parked or excluded item with its reason.
