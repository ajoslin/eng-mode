### Autopilot-full

**Drive a queue of independent PRs through verified landing when the operator grants merge authority. The root owns verdicts and coordination, never a PR.**

A verdict covers one patch and green CI covers one head. Step 4 runs the full three-lane round once, and again only for a major change. A single verifier or the patch-id rule in `shipping.md` carries a verdict to a new head, and every new head needs its own green CI.

1. Mark operator-owned items and PRs outside the queue. They stop at merge-ready. State the protocol and wait when asked for a plan. Begin writes only after an explicit go, then keep the falsifiable program objective in `goal` and the finite queue in `todo`.
2. Assign every PR one persistent accountable owner on an exclusive branch. That owner, or a named successor on the same branch, owns build and PR creation through **Opening a PR**, proof on the real surface through `verify-project`, triage, cleanup, the decision trail, Babysit to merge-ready, and any fix-forward. The root never implements or babysits a PR.

   The code is ready only after cleanup and `no-comments`, so the full round runs on finished code. The owner then rebases onto current trunk, whether or not trunk drifted, and reports the code-ready head SHA, so verification runs on the base the patch lands on. It reports every later head, and merge-ready once proof, CI, and Babysit pass. Fix rounds keep that base unless trunk conflicts or breaks CI, because each rebase restarts CI. Before the code-ready push and before any later push that needs a verifier, it runs the pre-review checks `project-standards` names for the touched paths on the committed head. A hook pass is not proof.

   Assume the owner's process dies. Soon after starting, it pushes and opens its decision trail per the **show-me-your-work** skill, then pushes after every verifiable unit (hooks on, a WIP commit is fine). Whoever starts a subagent records its id, state, and expected runtime (at least the longest past run of that kind) in an uncommitted `children.tsv` next to the trail, so the root can probe it if the parent dies. The owner force-pushes only its own branch, with `--force-with-lease` pinned to the SHA it last pushed or took over. On any push it did not make, it stops and reports to the root.
3. Run self-contained owners in parallel off trunk, never stacked, so each PR lands on its own. Serialize only genuinely overlapping writes. Route dependent work to **Autopilot-stack**.
4. **Verify once.** At the code-ready head SHA, the root commissions three independent lanes and aggregates `VERIFIED(<sha>)`: repository gates, live real-surface proof through `verify-project`, and receipts-plus-diff audit that distrusts the PR body. Run the audit as two or more review agents with the full brief, each with one main focus, such as consumer parity with trunk, lifetimes and races, or data and config safety. Pick each `task` item's `effort` for the job, per the Design and delegation section. Each lane returns `PASS`, `PASS+NOTES`, or `FAIL`, pinned to that exact SHA. Any `FAIL` blocks. The root never serves as a lane, and audits the receipts in the merge-ready report before the verdict. Post the verdict on the PR.

   Another full round runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets one verifier at the new head, which runs the repository gates and re-proves the load-bearing behavior through `verify-project`. Its `PASS` repins `VERIFIED` to that head. A lane result can also carry under the patch-id rule in `shipping.md`.

   Send every proven finding, whatever a lane labeled it, to the owner in one fix-forward. For each behavior finding, ask for a red test across every site with the same defect, or a repro receipt where no test can show it. A defect trunk shows without the PR is recorded against trunk and does not gate the PR. One the PR copies or newly reaches is the PR's own. Never push a fix yourself, because each branch has one writer. Replace a stuck owner instead.
5. **The owner lands only what the root verified, tested on the trunk it lands on.** It lands through **Shipping** with explicit merge authority, the root's countersign on the current `VERIFIED(<sha>)`, and Babysit merge-ready at that SHA. Green CI alone never authorizes a merge. Once the round's lanes have started, merge prep rebases onto current trunk, reports the new head, and waits for green CI.

   Before landing or applying `babysit complete`, run the mandatory final SHA-bound pre-merge gate in `eng-github`; earlier verification never substitutes for its fresh evidence and independent sign-off.

   Right before landing, fetch trunk and ask whether its changes can affect the patch, because rebasing for every trunk move never ends. Rebase and wait for CI when the code that would land was never tested: a `git merge-tree` conflict, a file both sides changed, or a change to which checks run for the PR. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head, because that install tests the lockfile that would land. When trunk changed a caller of the patch or something the patch depends on, such as code it calls or a dependency version, run the patch's checks on the merge result and land on a pass. Otherwise land. If trunk would force a third rebase past merge prep, hold and report to the root, which sequences the colliding work. After the merge, a fresh owner takes the next item, per Eng Mode's fresh-agents rule. Babysit and the root never merge.
6. **Run the root layer.** The root keeps the queue, ownership, liveness, and replacements. Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then the root's fresh countersign, because the owner is the one who wants green. Under a grant that covers approvals, that countersign is the approval, and the owner's record of it points at the countersign for a lane to check. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass an approval the forge enforces, because no countersign covers it.
7. Use only `eng-github` for PR state and watching. Freeze ordered PR references and head SHAs, then follow the labeled Bash async, `wait`, and snapshot sequence in `babysit.md` for each event. Classify each wake as `WAITING`, `READY`, `ADVANCE`, or `COMPLETE`. If an `eng-github` command exits 75, record the printed reset time and wait until it passes. Never retry the failed command before then or poll. Never fall back to raw `gh`, `curl`, or another tool. Use `eng-github api` or `eng-github graphql` for undocumented operations. If an operation is missing, stop. For repeated audit turns, use `loop` against the active goal with an event-driven wake or an hourly audit tick.
8. On every wake, re-read this playbook from trunk and fix drift, such as an unreported head or an unrecorded agent, by having its owner record it. Probe every owner and every agent in each `children.tsv`, and reconcile watch events, verdict SHA, Babysit state, and decision trail. Count only side effects as progress: commits, pushes, PR, check, or thread changes, proof receipts, or trail records. An agent is stuck when it errors, cannot start turns, or shows nothing new past its expected runtime. One waiting on the root or the operator is not stuck, so answer it. Replace a stuck owner at once with a named successor on the same branch, and have the owner replace a stuck subagent whose work is still needed, or do it yourself when the owner cannot. A stall never proves or drops the work. A tick that changed something for the operator ends by catching them up per the **ketchup** skill, and one that changed nothing stays quiet. End the loop only when no delegated work is left. After batched merges, run a retrospective and a post-merge review-comment sweep.
9. On an operator hold or stop, immediately send every owner a zero-write instruction and stop the loop. Each owner reports where it stands. Preserve branches, briefs, trails, watcher state, and queue placement for resumption.

**Reply:** catch the operator up per the **ketchup** skill. For each item, cover owner or successor, PR link, current head SHA, `READY` / `WAITING` / `ADVANCE` / `COMPLETE`, Babysit gate, `VERIFIED` verdict and lane receipts, countersign and why, merge or next action, operator gates, and decision-trail location.
